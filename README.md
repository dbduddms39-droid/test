# 일단확인 (MVP)

**입사 전, 근로조건부터 일단 확인하세요.**
채용공고, 처우·근로조건 안내(문자·메일 등, 선택), 근로계약서 중 **자료 한 건**으로 적힌 근로조건과 원문 근거를 기록하고, 지원·입사 **건별 기록**으로 남겨 새 안내가 오면 이어서 확인하는 웹앱입니다(PRD v3.1, v3.2 변경: [docs/spec/v3.2_변경명세.md](docs/spec/v3.2_변경명세.md)).
문서에 적힌 사실과 **원문 근거**만 보여 주며, 법률 위반 여부·계약의 효력·기업의 신뢰도·입사 적합성은 판단하지 않습니다.

- **문서별 역할 (v3.2)**: 채용공고·처우 안내는 **기록**(적힌 조건과 검증된 원문 근거만, 단독으로는 10개 기준의 미기재·불명확 표시와 확인 질문 없음, 협의 예정은 상태로만), 근로계약서는 **기재 상태 점검**(동결 기준표 v2.2 그대로). 문서 사이 비교는 모든 조합·순서로 합니다. 근로조건 없이 합격만 알린 안내는 '근로조건이 발견되지 않았어요'로 안내합니다.
- **원본 PDF 저장 (v3.2)**: PDF로 등록한 자료는 원본 파일을 같은 IndexedDB의 `files` 저장소(DB 버전 2)에 저장하고, 기록 상단에서 **원본 PDF 보기·다운로드**(저장된 Blob 그대로)를 제공합니다. 저장 순서는 원본 → 기록·확인 텍스트 → 분석 → 분석 결과이며, 분석에 실패해도 자료와 원본은 남고 '분석 실패'로 표시해 같은 텍스트로 다시 분석합니다(원본은 다시 저장하지 않음). 같은 기록의 같은 파일(SHA-256)은 한 번만 저장합니다. 예전 기록에는 원본이 없어 '이전에 등록한 자료는 원본 파일이 보관되어 있지 않아요'로 안내합니다.
- **자료 등록** (`#/new`, `POST /api/analyze` + `includeCriteria`): 문서 유형(채용공고·처우·근로조건 안내·근로계약서)을 고르고 텍스트를 붙여넣거나 사진·PDF를 올립니다(사진·PDF는 S03에서 추출 텍스트를 확인·수정한 수정본만 분석). 두 번째 문서를 요구하지 않습니다.
- **입사조건 기록** (`#/records/:id`, MVP 통합 QA 반영): 카드는 한 번만 보이고, 묶음 제목의 숫자 = 그 묶음의 카드 수입니다.
  - 채용공고·처우 안내 1개: 등록 완료 → 주요 조건 미리보기(항목명 · 값) → **비교할 두 번째 문서 추가하기**. 단독 분석 요약·확인 필요 집계·회사 질문은 없고, 전체 근로조건·원문·기록 관리는 접힌 보조 기능으로 둡니다.
  - 근로계약서 1개: 추가 확인이 필요한 조건 → 문서에 기재된 주요 근로조건 → 계산으로 확인한 조건 → 전체 조건·원문.
  - 문서 2개 이상(조합·순서 무관): 서로 다른 조건 → 새롭게 기재되거나 확인이 필요한 조건 → 같은 조건(접힘). 확인 질문은 해당 카드 안에서 보기·복사합니다.
  - 계산값: 근로계약서에 주 소정근로시간 숫자가 없어도 확인된 근무일·출퇴근 시각·휴게시간이 모두 있으면 '주 40시간 (계산값)'과 '계산으로 확인한 조건'으로 보여 줍니다(`weeklyCalc`, 판정은 동결 기준표 그대로, 근거가 부족하거나 충돌하면 계산하지 않음).
  - 같은 금액 + 추가 세부 조건: '3,600만 원'과 '36,000,000원'은 같은 금액으로 보고, 뒤 자료에만 적힌 월 지급 기준액·지급일은 '같은 내용 · 세부 조건 추가'로 원문 조각 그대로 안내합니다.
  - 요약 값에서는 원문 목차·항목명('2. 근무장소', '7. 수습기간 및 수습 중 임금')을 빼고, 원문 근거 화면에는 그대로 둡니다. 화면 항목명은 '임금'으로 통일합니다(기준표 주제명은 그대로).
- **새 안내 추가** (`#/records/:id/add`): 같은 기록에 자료를 덧붙입니다. 이전 자료의 텍스트·분석·원문은 바꾸지 않고, 항목마다 `같은 내용으로 안내됐어요 / 서로 다른 안내가 있어요 / 이번 안내에 새롭게 적혔어요 / 이번 안내에서는 확인되지 않아요 / 서로 비교하기 어려워요 / 분석 확인 불가`를 보여 줍니다(`public/relate.js`, AI 재호출 없음).
- **항목 상세** (`#/records/:id/item/:no`): 자료별 세부 기준·원문, 관계 이유, 질문, **내가 기록한 답변**(선택 메모, 작성·수정·삭제).
- **내 기록** (`#/records`): 기록 목록·삭제·저장 범위 안내. 기록은 브라우저 IndexedDB에만 저장합니다(`public/store.js`, 저장 후 다시 읽어 확인한 뒤에만 '저장했어요'; 실패하면 '저장되지 않았어요'와 다시 저장).
- `POST /api/compare`(2문서 비교 API)는 남아 있지만 화면에서는 쓰지 않습니다. 비교 규칙은 `public/compare-core.js`로 옮겨 브라우저(기록의 자료 간 관계)와 서버가 함께 씁니다.

문서별 추출·근거 검증·기재 상태 판정은 **점검 기준 v2.2**(10개 주제, 32개 세부기준)를 따릅니다.
판정 기준의 단일 원천은 동결 기준표 `design-handoff/spec/04_점검기준표_v2.2_동결원문.md`입니다.

## 실행 방법

Node.js 20 이상이 필요합니다. AI 분석은 **Google Gemini API 무료 등급**(`gemini-3.5-flash-lite`)을 사용하며, 유료 모델로 자동 전환하지 않습니다.

```bash
npm install
# GEMINI_API_KEY 는 서버 환경변수로만 등록합니다 (코드·채팅·브라우저에 넣지 않음).
npm start                 # 실제 AI 분석, http://localhost:3000
npm run demo              # DEMO_MODE=true — 키워드 규칙 데모 (AI 아님)
```

- 키 발급: Google AI Studio(https://aistudio.google.com/apikey)에서 **결제 수단을 연결하지 않은 프로젝트**로 발급하면 무료 등급으로만 동작합니다. 결제(billing)를 켜면 유료 요금이 적용될 수 있으니 켜지 마세요.
- `GEMINI_API_KEY`가 없으면 데모로 바뀌지 않고, 분석 요청에 "AI 분석이 아직 설정되지 않았어요" 오류를 안내합니다.
- 데모 모드는 `DEMO_MODE=true`를 명시했을 때만 켜집니다. 데모 결과는 헤더 배지와 결과 화면 안내로 AI 결과와 구분됩니다.
- 무료 사용량 한도(HTTP 429)에 도달하면 "AI 무료 사용량 한도에 도달했어요"를 안내합니다.

### 이미지·PDF 업로드

- 입력 화면에서 **캡처 이미지 최대 5장**(JPG·PNG·WebP) 또는 **PDF 1개**를 올릴 수 있습니다 (파일당 10MB, PDF 10쪽, 스캔된 쪽 5쪽까지). 근로조건 비교에서는 문서 A·B마다 따로 올리고, S-03에서 확인한 텍스트를 그 문서의 내용으로 씁니다(문서마다 입력란·추출 상태·이미지 목록을 따로 유지).
- 여러 장의 이미지는 **같은 문서의 연속 캡처**로 봅니다. 미리보기·개별 삭제·순서 변경(위로/아래로) 후 '텍스트 추출'을 누르면 정한 순서대로 한국어·영어 글자를 인식해 하나의 편집 가능한 문서로 합칩니다. 일부 이미지가 실패하면 나머지는 합치고 실패한 장을 표시합니다.
- **파일은 브라우저 안에서만 처리하고 서버로 보내지 않습니다.** 일반 PDF는 pdf.js로 텍스트를 추출하고, 이미지와 스캔 PDF 쪽은 Tesseract.js로 OCR 합니다.
- OCR 전처리(`public/ocr-prep.js`): 작은 칸마다 바탕 밝기를 구해 바탕이 비슷한 영역별로 '흰 바탕 위 검은 글자'로 맞춥니다. 색 배너·버튼의 흰 글자, 다크 모드 화면, 일부만 어두운 배너, 회색 칩·표 머리글을 모두 같은 방식으로 처리합니다(이전에는 어두운 가로줄 전체만 반전해 중간 밝기 배너 글자를 놓치고, 일부만 어두운 배너는 줄 전체가 망가졌습니다). 글자 크기를 재서 작은 글자(저해상도·메신저로 받은 캡처)는 키우고, 표 테두리·버튼 외곽선 같은 긴 직선과 가장자리 잔상을 지우고, 흰 여백을 둡니다.
- 제한적 재인식: 인식 결과에서 신뢰도가 낮은 단어가 있는 줄만(이미지마다 최대 8줄) 전처리 이미지·원본 이미지·1.5배 확대 이미지에서 한 줄씩 다시 읽고, 더 확실한 결과(평균·최저 단어 신뢰도)를 고릅니다. 모든 후보는 같은 이미지에서 실제로 읽은 글자이며, 글자를 추측해 고치지 않습니다. 칸 사이 빈 곳·테두리에서 생긴 기호 조각('_', '|')과 신뢰도 낮은 괄호 조각만 지웁니다.
- 배치에 맞춘 줄 엮기(`public/ocr-layout.js`): 정리된 이미지에서 행(가로 빈 띠)과 칸(넓은 세로 빈 곳)을 찾아, 인식된 단어를 위치대로 칸에 넣고 '항목명 + 값의 첫 줄', 값의 나머지 줄 순서로 다시 엮습니다. 표의 아이콘 칸(한글이 없거나 아이콘 크기에 확신이 낮은 칸)은 빼고, 행 가운데의 아이콘은 새 항목의 시작으로 봐서 좌우 2열 목록(복리후생 등)을 한 줄에 하나씩 나눕니다. Tesseract가 두 줄짜리 값 가운데의 항목명을 위아래로 잘라 읽거나(예: '근무시간' → '근' + '=e') 아이콘과 붙여 읽는 문제가 있어, 칸이 여러 개인 행은 칸마다 따로 다시 읽고 전체 인식보다 확실하거나 칸을 더 많이 덮는 결과를 고릅니다(전체 OCR만 / 배치만 / 배치+칸별 OCR 비교는 [docs/ocr-accuracy-report.md](docs/ocr-accuracy-report.md)).
- 결과 평가: 이미지마다 신뢰도와 함께 '확인할 부분'(신뢰도가 낮거나 `2O27`·`202712.31`처럼 숫자 사이에 글자가 섞이거나 날짜·시간에 없는 형태의 숫자, 한글 문서에서 신뢰도 낮게 영문으로 읽힌 단어 예: '스낵바' → `Addl`)와 '일부만 읽힘'(이미지에서 찾은 글자 줄 수보다 읽힌 줄이 크게 적음)을 판단해, 이미지 목록과 안내 문구로 원본과 비교할 곳을 알려 줍니다. 값은 인식한 그대로 보여 주고 고치지 않습니다.
- 정확도 비교: `node scripts/ocr-bench.mjs` (가상 채용공고 이미지 17장 `test/fixtures/ocr-bench/`(생성: `scripts/make-ocr-bench-fixtures.mjs`)과 실제 서비스에서 오류가 난 오퍼 안내문 캡처 2장 `test/fixtures/ocr-real/`(이름은 [이름]으로 가려진 이미지, 정답은 원본을 보고 옮겨 적음)). 수정 전후 비교 결과는 [docs/ocr-accuracy-report.md](docs/ocr-accuracy-report.md)에 있습니다.
- 추출 결과는 **S-03 추출본 확인** 화면에 원본 미리보기와 함께 편집 가능한 텍스트로 보여 주고 **자동으로 분석하지 않습니다.** '내용 확인하고 분석하기'를 눌렀을 때 확인·수정한 텍스트만 분석 API로 전송됩니다. 결과·상세 화면에는 '추출·확인한 텍스트 기준'임을 표시합니다.
- 직접 입력한 텍스트와 파일에서 추출한 텍스트는 따로 보관합니다. 화면 이동·뒤로 가기·재시도 중에는 이 창의 메모리에 유지되고, 새로고침하거나 창을 닫으면 사라집니다.
- 형식 오류·인식 실패·일부 실패·바꾸기 취소 때 이미 입력한 내용과 이미지 목록은 그대로 둡니다.
- 라이브러리와 언어 데이터는 외부 CDN이 아니라 같은 사이트의 `public/vendor/`에서 제공합니다 (처음 업로드할 때만 내려받음: PDF 약 2MB, OCR 약 8.5MB). `public/vendor/`는 `npm run vendor`로 `node_modules`에서 복사해 커밋한 파일입니다. Vercel은 빌드 스크립트보다 먼저 `public/`을 정적 파일로 수집하므로 빌드 때 생성하지 않고 커밋해 둡니다.
- 한계: OCR은 사진 품질·글꼴·기울기에 따라 오타가 생깁니다. 신뢰도가 높은데도 틀리는 비슷한 글자(예: 'OO'→'00', '응'→'음', '금'→'급', '헤'→'해', '·'→'-', 'D-12'→'0-12')는 표시되지 않을 수 있습니다. 작은 글씨의 일부 단어는 크기를 바꿔도 Tesseract 한국어 모델이 읽지 못해(예: '스낵바', '필요한') '인식이 불확실한 부분'으로만 알려 줍니다. 심하게 흐린 부분은 읽지 못하며 S-03에서 '일부가 빠졌을 수 있어요'(추정)로 알리고, 확인 표시 전에는 분석하지 않습니다. 표 테두리가 '_' 같은 기호로 섞일 수 있고, 여러 단 배치는 줄 순서가 섞일 수 있습니다. 연속 캡처가 겹치면 겹친 줄이 두 번 들어가므로 직접 지워야 합니다. 처음 OCR 때 내려받는 데이터 때문에 느린 네트워크·저사양 휴대폰에서는 시간이 걸립니다. 암호가 걸린 PDF는 열지 않습니다.

### 자료 간 비교 규칙 (`public/compare-core.js`, `src/compare.js`는 재수출)

- 두 문서를 각각 기존 분석(추출 → 인용 검증 → v2.2 규칙)으로 처리한 뒤, 비교 단계에서는 AI를 다시 부르지 않고 규칙으로만 비교합니다. 문서 순서는 채용공고 → 오퍼 안내 → 근로계약서 단계로 정렬합니다(앞 단계 A, 뒤 단계 B).
- 상태: 동일한 조건 / 달라진 조건 / 새로 추가된 조건(앞 문서에 없고 뒤 문서에 적힘) / 한쪽 문서에서 확인되지 않음 / 비교 불가 · 추가 확인 필요(간략한 오퍼 안내에 없는 조건) / 모호하거나 직접 비교하기 어려움 / 두 문서 모두 확인되지 않음 / 분석 확인 불가 / 해당 없음.
- 한쪽 문서에 없는 조건을 삭제·변경으로 보지 않습니다. '추후 협의'·'회사 내규에 따름' 같은 표현이나 한 문서 안의 서로 다른 값은 구체적인 조건으로 보지 않습니다.
- 금액·시간 등은 두 문서의 산정 단위(연봉·월급·시급, 주·1일)가 같고 값을 하나로 특정할 수 있을 때만 차이를 계산합니다(단위 환산 없음, 세전·세후가 다르면 비교하지 않음). 장소·업무 같은 글은 표기를 정리해 같을 때만 '동일'로 보고, 다르면 같은지 추측하지 않습니다.
- 모든 비교 결과에 두 문서의 검증된 원문 인용(줄 번호)을 붙입니다. 한 문서라도 AI 분석에 실패하면 결과를 만들지 않고 오류로 안내합니다. 비교 1건은 요청 제한에서 분석 2회로 셉니다.

### 지금 확인할 내용 (`public/followups.js`)

- 우선 확인(최대 3건): 자료 사이의 서로 다른 구체 값, 한 자료 안의 서로 다른 값, 근로계약서의 모호한 주요 내용, (조건부) 근로계약서에서 주요 항목을 찾지 못함·오퍼의 핵심 조건이 정해지지 않음. 나머지는 '추가로 확인할 내용'으로 접습니다.
- 채용공고·처우 안내 단독으로는 미기재·불명확 질문을 만들지 않습니다(v3.2, 한 문서 안에 서로 다른 값이 함께 적힌 경우만 예외). 다른 자료에서 확인된 항목은 '찾지 못함'으로 묻지 않습니다. 분석 전·분석 실패 자료는 비교·질문에서 빠집니다.
- 질문 목록('지금 확인할 내용'·'추가로 확인할 수 있는 질문')에는 실제 질문 문장이 있는 항목만 넣습니다. 처음 적힘·구체화처럼 질문이 없는 상태 안내는 맨 위 요약·핵심 조건 카드·전체 목록에서 보여 줍니다.
- 담당업무처럼 글로 적힌 조건은 쉼표·'및'으로 나뉜 항목 단위로 비교합니다(표현·띄어쓰기·'업무' 같은 말 차이는 같은 내용). 한쪽에만 적힌 항목이 있으면 그 원문 조각을 그대로 넣어 구체적으로 묻고(업무가 늘었다고 단정하지 않음), 특정할 수 없으면 질문 없이 원문 비교를 안내합니다.
- 근로계약서 근무시간처럼 핵심 내용(출퇴근 시각·휴게시간)은 적혀 있고 주 소정근로시간 숫자만 직접 적혀 있지 않은 '일부 확인'은 판정을 바꾸지 않고 '세부 확인 필요'와 '출퇴근 시각·휴게시간은 적혀 있어요. 주 소정근로시간은 별도로 확인이 필요해요.'로 '내용이 모호함'과 구분합니다.
- 분석 확인 불가(근거 검증 실패·OCR 불확실)는 회사 질문을 만들지 않고 '같은 텍스트로 다시 분석하기'를 안내합니다.
- 뒤 자료에 처음 적힌 조건은 바뀜으로 보지 않고, 계약기간·수습기간·수습 중 급여만 확정 여부를 묻습니다. 수습기간과 수습 중 급여 질문은 하나로 묶습니다.
- 질문은 템플릿(AI가 쓰지 않음)이며 검증된 원문 값만 넣습니다. 고쳐 쓰고 복사할 수 있고, 일단확인은 보내지 않습니다.

## 테스트

```bash
npm test             # 단위·통합 테스트 (실제 AI 호출 없음)
npm run report       # 가상 문서 F01~F11을 데모 분석기(AI 아님)로 실행 → docs/test-report-demo.md
npm run eval:live    # 가상 문서 F01~F11을 실제 Gemini API로 실행 → docs/test-report-live.md (GEMINI_API_KEY 필요, 실제 API 호출)
npm run eval:live -- --samples=F02,F05   # 일부 문서만 실행 (무료 사용량 절약)
```

- 규칙 엔진 테스트(`test/rules.test.js`)는 F01~F11(`test/v22-fixtures.js`, 출처 `design-handoff/tests/`)과 R01~R29 짧은 예시로 **서버의 인용 검증·상태 규칙**이 기획상 기대 판정(오라클)과 같은지 확인합니다. 여기서 AI 응답은 사람이 작성한 '올바른 추출값'이므로, **실제 Gemini의 정확도는 검증하지 않습니다.** AI가 잘못 답한 경우(허위 인용, 주 5일을 휴일로 인용, 단위 없는 급여를 확인됨으로, 포괄 문구 인용 등)에 서버 규칙이 막는지도 따로 확인합니다.
- `eval:live` 보고서는 기획상 기대 판정과 실제 실행 결과를 나란히 적습니다. 일치율은 측정값이며 모델 정확도 검증 완료를 뜻하지 않습니다.
- 문서는 모두 가상 문서입니다. 무료 등급 API에는 실제 개인정보가 담긴 문서를 넣지 마세요.

## 개인정보

- 입력 화면에 개인정보(이름·연락처·주민등록번호·주소) 가림 안내, 확인한 텍스트가 일단확인 서버를 거쳐 외부 AI(Google Gemini API)로 전달되고 그 내용에는 제공자의 데이터 처리 방침이 적용된다는 안내, 결과가 이 브라우저에 저장된다는 안내를 표시합니다.
- 서버는 원문·결과를 저장하지 않고, 로그에는 세부기준 ID·오류 코드·단위 개수만 남깁니다.
- 기록(확인한 텍스트·분석 결과·원문 근거·기록 이름·답변 메모, PDF로 등록한 자료의 원본 파일)은 브라우저 IndexedDB(`ildan-hwagin` 데이터베이스)에만 저장합니다. 계정·동기화가 없어 다른 기기·브라우저에서는 보이지 않고, 시크릿 창·사이트 데이터 삭제·저장 공간 부족으로 사라질 수 있습니다. 화면 안내: "파일은 현재 브라우저에 저장됩니다. 다른 기기에서는 확인할 수 없으며 브라우저 데이터 삭제 시 함께 사라질 수 있습니다." 사진 원본은 저장하지 않습니다. 원본 파일은 서버로 보내지 않고 내용을 로그에 남기지 않습니다.
- 기록 삭제는 한 항목(기록)에 담긴 자료·텍스트·분석·원문·원본 PDF·메모를 함께 지웁니다(다른 기록의 원본은 그대로). 이미 분석을 위해 전송된 요청은 되돌릴 수 없습니다.
- 업로드한 파일은 서버로 전송하지 않고 브라우저 메모리에서만 처리합니다. Tesseract.js는 언어 데이터(문서 내용 아님)만 브라우저 저장소(IndexedDB)에 캐시합니다.
- Gemini API **무료 등급**은 유료 등급과 데이터 처리 조건이 다를 수 있습니다(제출 내용이 Google 서비스 개선에 쓰일 수 있음). Gemini API 추가 약관을 확인하기 전까지는 가상 문서로만 테스트하세요.
